Auditoría técnica de PRE gratuita o de coste mínimo

Proyecto AELB · Precios/free tiers verificados: 20 de agosto de 2026

Conclusión: sí. Desplegaría PRE en una VM Always Free de Oracle Cloud con Docker Compose, MySQL persistente, Mailpit, Caddy y S3 AWS real.

1. RESUMEN EJECUTIVO

La arquitectura más adecuada para probar la aplicación completa durante meses es una VM ARM Always Free de Oracle Cloud. Permite ejecutar el mismo modelo Docker que posteriormente puede trasladarse a EC2, mantiene frontend, backend, MySQL y Mailpit en la misma red, evita problemas de cookies/CSRF mediante un reverse proxy same-origin y no duerme.

Coste esperado: 0 €/mes de infraestructura, o aproximadamente 0–0,30 €/mes usando un bucket S3 AWS separado para PRE. El dominio y Cloudflare DNS no añaden coste si el dominio ya existe.

El backend no debe ejecutarse con 256 MB. 512 MB es posible con JVM limitada; 1 GB es el mínimo cómodo. Oracle ofrece recursos suficientes para ejecutar también MySQL y el frontend.

5. FRONTEND

Vercel soporta correctamente SSR, Server Components, rutas dinámicas y route handlers, pero su Hobby está restringido a uso personal/no comercial. Render puede ejecutar el Dockerfile actual, aunque con 512 MB, 0,1 CPU y suspensión tras 15 minutos. Netlify y Cloudflare requerirían adaptar el runtime a sus modelos.

La opción más coherente con el despliegue posterior es ejecutar el frontend standalone en Docker dentro de la VM Oracle.

6. BACKEND

Render y Koyeb pueden ejecutar Java 21 mediante Docker, pero sus límites gratuitos son ajustados. El sleep detiene el EmailWorker y genera cold starts. Oracle permite ejecutar el backend con memoria holgada, Docker Compose y sin suspensión.

Para PRE, un cold start de aproximadamente un minuto sería aceptable, pero no es necesario aceptarlo en Oracle. El arranque de Spring Boot dependerá de JVM, MySQL y migraciones; debe probarse con el healthcheck de readiness.

7. MYSQL

Aiven ofrece MySQL gratuito indefinido, sin tarjeta, con 1 CPU, 1 GB RAM, 1 GB de almacenamiento y backups. Puede apagar servicios sin actividad prolongada y limita conexiones. Es la mejor DB gestionada gratuita.

Mi preferencia es MySQL 8.4 dentro de la VM Oracle con volumen persistente: misma versión, red privada, menor latencia y backups controlables. No recomiendo cambiar temporalmente a PostgreSQL; el repositorio usa driver, dialecto, esquema y migraciones MySQL.

8. STORAGE

Usaría un bucket S3 AWS real y separado para PRE. Es la mejor forma de probar presigned URLs, CORS y permisos similares a producción. Para el volumen previsto el coste posterior al free tier sería de céntimos. MinIO debe mantenerse para local; R2 es válido, pero introduce diferencias innecesarias.

9. STRIPE

Stripe Test Mode permite Checkout, webhooks, tarjetas de prueba y pagos sin movimiento de fondos. Configurar un webhook público HTTPS en https://pre.midominio.es/api/webhooks/stripe con claves y webhook secret exclusivos de PRE. Nunca usar claves live.

Documentación oficial de testing de Stripe.

10. EMAIL

La opción más segura es Mailpit dentro de la VM, con SMTP interno en el puerto 1025. El panel debe exponerse solo por SSH tunnel, Cloudflare Access o Basic Auth. Así se prueban registro, verificación y password reset sin posibilidad de enviar cientos de correos reales.

SES es técnicamente posible, pero no es la opción segura por defecto. Además, el free tier específico de SES cambió en julio de 2026; las nuevas cuentas dependen de los créditos AWS generales. Anuncio actual de SES.

11. DOMINIO / HTTPS / COOKIES

Usaría https://pre.midominio.es como único origen público y Caddy enrutaría /api/* al backend. Esto evita los problemas actuales del frontend con la cookie CSRF: api-pre.midominio.es sería otro origen y la aplicación lee XSRF-TOKEN mediante document.cookie.

Configuración PRE: AUTH_COOKIE_SECURE=true y, con same-origin HTTPS, AUTH_COOKIE_SAME_SITE=Strict. Cloudflare DNS y TLS son gratuitos si el dominio ya existe.

15. LIMITACIONES DE PRE GRATUITA

No será una réplica de producción: no probará de forma equivalente alta disponibilidad, Multi-AZ, failover RDS, autoscaling, ALB, IAM idéntico, CloudWatch, WAF AWS ni rendimiento bajo carga. Sí permitirá probar HTTPS, cookies Secure, JWT, CSRF, CORS, login, registro, password reset, emails capturados, inscripciones, Stripe Test/webhooks, uploads, MySQL, migraciones, Docker y healthchecks.

19. PLAN PASO A PASO

  1. Crear cuenta Oracle, elegir región y verificar capacidad ARM.
  2. Crear VM de 2 OCPU, 12 GB RAM y volumen de 50–100 GB.
  3. Instalar Linux, Docker Compose, firewall y acceso SSH.
  4. Configurar Cloudflare DNS para pre.midominio.es.
  5. Crear bucket S3 PRE privado y CORS.
  6. Crear secretos PRE fuera del repositorio.
  7. Levantar MySQL con volumen y ejecutar schema/migraciones.
  8. Levantar Mailpit sin exposición pública directa.
  9. Desplegar backend con perfil PRE y Actuator.
  10. Desplegar frontend con API relativa /api.
  11. Configurar Caddy y HTTPS.
  12. Configurar Stripe Test webhook.
  13. Crear seed de datos falsos.
  14. Configurar push → build → deploy → smoke tests.
  15. Configurar backups MySQL y prueba de restauración.
